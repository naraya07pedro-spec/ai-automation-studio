# Slice 77 · Frozen tool registry + owner-confirmed local JSON action

## User-facing capability

The local agent now exposes a **code-owned, effect-classified tool registry** and one narrow, two-phase, permissioned action to turn a completed, explicitly approved CSV profile into a **machine-readable JSON file** in the local workspace.

This is a genuine local file creation, not another AI response or conceptual connector. The first action deliberately **cannot** be proposed as a tool-plan step and **cannot** enter the existing server-owned read-only batch. This avoids converting previously reviewed read permissions into general file-writing authority.

Enable only by explicitly starting the authenticated loopback server with *all* options:

```powershell
python app/local_server.py --enable-local-agent --enable-agent-plans --enable-plan-csv --enable-plan-artifacts --enable-plan-actions
```

No Windows/Ollama real-device acceptance is claimed.

## Registry / effect policy

The frozen `app/local_tool_registry.py` has nine named capabilities. The eight preexisting plan tools remain either `READ_ONLY`, `PUBLIC_READ` (separate owner-allowlisted repository grants), or `SELECTED_SNAPSHOT_READ` (only selected documents/CSV). These eight names are **the source of truth for the batch read-only allowlist**. The ninth, `local_csv_profile_json_export`, has effect class `LOCAL_CREATE_ONLY`, `batch_allowed=false`, `model_plannable=false`, `owner_confirmation_required=true`.

`GET /api/local-agent-capabilities` now includes `tool_registry`: one stable list with names, effect class, whether enabled by startup flags, batch permissions, owner-confirmation requirement, model-plannability and descriptive scope. This is metadata, **not** dynamic plugin loading, arbitrary adapter discovery, shell exposure or external provider auth.

## Exact approval path

1. Owner explicitly selects a short CSV, consents to its **local plaintext SQLite storage**, reviews and approves a bounded plan containing a CSV profiling step, and completes it. No automatic write happens at any earlier stage.
2. **Preview CSV profile JSON (no write)** calls authenticated, same-origin and CSRF-protected `POST /api/local-agent-action-preview`, with **exactly** `{"action":"local_csv_profile_json_export","plan_id":"<id>"}`. The server revalidates the COMPLETE stored deterministic CSV profiles against the original source and reviewed selected columns. No browser body, path, filename, URL, or content parameter is accepted.
3. The preview returns the complete **aggregate-only JSON content**, bytes, SHA-256 and fixed destination `~/.ai-automation-studio/exports/local-agent-csv-profile-<plan-id>.json`, plus a cryptographically random **single-use ticket expiring after 300 seconds**. The ticket exists only in server memory and expires on restart. Preview does **not** write a file, call an LLM, fetch a network resource or start a tool.
4. **Confirm & save verified JSON** displays another native confirmation showing exact filename, SHA-256, byte count and effects. Declining confirmation leaves the ticket unused and writes nothing. Accepting makes a separate protected `POST /api/local-agent-action-commit` request with exact fields `action`, `plan_id`, `preview_token` and `preview_sha256`; no new CSV content or output path is accepted.
5. Server consumes the ticket **once**, revalidates original source and full saved profiles and confirms the entire generated byte stream matches the preview SHA-256. Only after the fixed `LOCAL_CSV_PROFILE_EXPORT / ATTEMPT` security-audit record is persisted does the server create the file using exclusive temporary file + create-only hardlink. It never overwrites an existing target. Identical content returns `EXISTS_IDENTICAL` with zero new writes; changed files, directories or symlinks fail closed.
6. The durable security audit records `SUCCESS` or `FAILED` without JSON bodies, filenames, tokens or CSV rows. A missing audit readiness **blocks the write**. If the audit fails after disk creation, the API returns **unknown outcome**, not an invented success; the user must inspect the local workspace and explicitly preview again to recover an idempotent result.

File size is capped at **32 KiB**. Only deterministic profiles are exported; no raw cells, free-form model interpretations, passwords, secrets, private documents, arbitrary paths, shell commands, emails or external uploads. Existing local security-audit and workspace permission/symlink checks apply.

## Guarantees versus limitations

- Authenticated + origin/host restrictions + CSRF remain active; the two endpoints are not allowed in public/demo routes. Startup requires `--enable-plan-actions` **and** both CSV and artifact opt-ins. Restart revokes outstanding preview tickets. No silent retries.
- The registry is **static**; there is no remotely installable tool code. It is a foundation for later integrations with effect scope, schema, human confirmation and audit policy, not a full external connector runtime.
- The original CSV remains **plaintext in the owner-local SQLite database**. The JSON output contains aggregates and source filenames/hashes. Even aggregate values can be sensitive. Do not use private customer data, secrets or personal records.
- A SHA-256 digest detects mismatches between snapshots and output, but cannot stop an attacker who can rewrite every field and hash in the same local state. Source truth, semantic financial correctness, and model interpretations are not independently verified.
- No generic write tool enters the plan, no server batch may execute the action, and no scheduled write is available. The create-only file survives a browser close/restart; unspent permission tickets do **not**.
- Verification uses synthetic Python, authenticated HTTP, Chromium browser and disposable Windows runners. It does **not** test the real owner's Windows account, filesystem ACL or Ollama model. Owner PC validation remains deferred at GitHub Issue #68.

## Follow-on after this slice

Next substantive milestone is a **narrow explicit external-service connector** (first in read-only mode) through this registry, with precise per-account/per-resource grants and provenance, before introducing any external mutations. A write-capable connector needs a separate per-action approval/side-effect preview and idempotency/uncertainty handling: the registry alone does not grant it.
