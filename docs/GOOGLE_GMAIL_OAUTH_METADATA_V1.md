# Native Google OAuth + Gmail metadata-only connector (v1) · 2026-11-06

## Scope actually implemented
This is the first **provider-specific Google OAuth 2.0 integration**, separate from managed HTTPS/n8n webhook registrations. It is **Gmail metadata-only**, not Gmail sending, Google Drive/Calendar, CRM, WhatsApp, automatic schedule polling, arbitrary MCP tools, or a ChatGPT plugin bridge. The enabled server exposes **only two owner-clicked actions**: Gmail account counters and up to five inbox message headers (From, Subject, Date, unread). No email body is requested. Model tools and the recurring scheduler cannot call Gmail.

The browser dashboard is Mission Control section **09 · Google Gmail metadata**. Its status endpoint checks whether an encrypted local grant exists and is readable; it does not contact Google. Every actual Google API read requires a live local owner session, valid CSRF on POST, the **current owner password**, and an available security audit ledger. That read may expose subject/sender to the owner's browser, never to an AI model.

## Official Google setup on the Windows PC
1. In [Google Cloud Console](https://console.cloud.google.com/), create or choose your own project, enable **Gmail API**, configure the OAuth consent screen, and create an OAuth **Desktop app** client ID. For testing-mode apps, add your Google account as a test user. Read Google's current consent/verification and restricted-scope requirements; the Gmail metadata scope is classified **restricted** and may impose additional verification/security-assessment requirements for public distribution.
2. Update your Studio checkout. Install the optional real encryption dependency: \`python -m pip install -r requirements-vault.txt\`.
3. Reuse the already backed-up independent \`AAS_VAULT_MASTER_KEY\` from the previous AES-GCM vault stage. It must be the SAME key for enrollment and subsequent Studio startup. The enroll command also supports a hidden terminal prompt if the environment variable is not defined. Never paste the key, OAuth authorization codes, client secrets or tokens into ChatGPT or GitHub.
4. From the checked-out project root run \`python tools/connect_google_gmail.py --client-id YOUR_GOOGLE_DESKTOP_CLIENT_ID\`. The one-shot tool opens the official Google browser consent flow using a random loopback TCP port, PKCE S256 verifier/challenge, and one-time state. It waits for the loopback callback, exchanges the authorization code only with Google's token endpoint, checks that the granted scope includes **exactly the required metadata permission**, and seals the returned refresh token.
5. If Google supplies a Desktop application client secret that your configuration requires, set \`AAS_GOOGLE_CLIENT_SECRET\` privately in the same PowerShell session before enrollment. The optional secret is stored only in the encrypted grant along with the refresh token. Do not share it or commit it.
6. Launch: \`.\START_AI_STUDIO.cmd --mode offline --enable-google-gmail-metadata\`. Log in at \`http://127.0.0.1:8765/mission\`, open section 09, refresh status, enter your current **Studio owner password** and click the specific read button. Connection is disabled by default without the feature flag.

To replace an existing readable grant, explicitly re-enroll with \`--replace\`; no automatic replacement occurs. To clear the **local** encrypted grant only, use \`python tools/connect_google_gmail.py --disconnect-local\`. This does **not** revoke permissions already granted at Google; remove app access separately in your Google Account security settings if you intend to revoke remotely. Local unlink is not secure erasure of old SSD blocks or backups.

## Privacy, durability and risks
- Scope: \`https://www.googleapis.com/auth/gmail.metadata\`. It cannot authorize Gmail sending or modification. This is **not** the same as giving the application access to an existing ChatGPT Gmail plugin, whose connection is separate.
- Vault file: \`~/.ai-automation-studio/google-gmail-vault.json\`; **distinct authenticated encryption AAD** from the managed webhook vault. The separately supplied 256-bit master key is never saved beside this file. Old managed-webhook ciphertext remains decryptable under its unchanged AAD. No plaintext fallback.
- The actual Google API clients call only hardcoded official HTTPS hosts and paths, with no redirect following. Network failures use generic redacted errors. Each read fetches a fresh access token from the encrypted stored refresh token; no background refreshing, push notifications, sending, or scheduler grants.
- Local loopback browser callback and Studio's loopback-only HTTP are **not safe to publish directly on the internet**. The Desktop OAuth enrollment flow is for a PC with a real system browser. Do not run this installer blindly on the Tencent VM or try to expose callback ports publicly.
- Refresh grants can be revoked/expired by Google; testing-mode grants may be short-lived. Provider verification restrictions, quotas, owner consent and live network success are outside CI.
- AES-GCM at rest does not defend against full compromise of the same OS account or master-key exposure via process environment. Windows NTFS ACL verification, KMS/HSM and automatic key rotation remain open.
- **Not live verified**: no Google Cloud OAuth Desktop client ID, real consent, actual Gmail API response, n8n production send, or Tencent 24/7 deployment has been supplied/tested. CI uses synthetic access/refresh tokens with injected Google transport. A successful PR is code-quality evidence, not verified real Gmail access.
