# Stage #117: Independent read-only n8n execution verification

Recorded: November 7, 2026 WIB. Local-first, no Tencent VPS or live credentials used by CI.

## The engineering advance

Stage #114 holds a durable owner-approved one-shot webhook delivery receipt. Stage #116 holds a signed, owner-imported n8n final-step claim, validated with the managed encrypted connector secret. Neither alone proves the provider independently executed the job.

Stage #117 adds one explicit, owner-password-approved **official n8n Public API read** for the exact signed execution ID. The checker requires all three identities:
1. Numeric n8n execution ID exactly equal to the previously signed receipt.
2. Provider workflow ID exactly equal to the owner-pinned n8n workflow configuration.
3. Original local workflow ID, event ID and delivery ID inside the **single item of a specifically named incoming Webhook node** in the real execution's saved node data.

Only these exact matches, combined with n8n's finalized execution status, can produce EXECUTION_SUCCESS_CORRELATED or EXECUTION_FAILED_CORRELATED. This means an **n8n execution and incoming delivery are verified**, not that a CRM, customer, email or payment was successfully changed.

### Official API references

- https://docs.n8n.io/api/api-reference/
- https://docs.n8n.io/api/authentication/
- https://docs.n8n.io/api/

Public n8n API availability is account/plan dependent; n8n's free trial may not include API access. Authentication uses the X-N8N-API-KEY header. Prefer a key scoped to execution:read where the edition supports it. No user credential is included in this repository, and local CI substitutes synthetic responses.

## Lightweight activation

The verifier is **disabled by default**. It can reuse an existing completed-plan ledger from Stage #114 without starting Ollama or paying OpenAI. The following values must be explicitly provisioned outside source control using the existing allowlisted runtime-secret mechanism:

- AAS_VAULT_MASTER_KEY: existing private AES-256-GCM connector registry master key.
- AAS_N8N_API_KEY: the separate public API key for the owner-controlled n8n account.
- AAS_N8N_API_ORIGIN: strict public HTTPS origin of the chosen instance, for example https://YOUR-INSTANCE.app.n8n.cloud (no URL path, port override, IP literal, localhost, query or credentials).
- AAS_N8N_WORKFLOW_ID: exact n8n workflow ID (distinct from the internal AI Automation Studio workflow ID).
- AAS_N8N_WEBHOOK_NODE_NAME: exact incoming Webhook node name. The verifier examines only this configured node's saved output in the n8n execution response.

Use the local startup flags: **--enable-encrypted-managed-webhooks --enable-n8n-execution-verify**. The newly enabled verifier loads an existing plan store without starting a model. No new plan is generated by this mode; a completed previously approved plan and its exact signed handoff must already exist. The private operator URL is http://127.0.0.1:8765/handoff.

## Owner operation

1. Inspect the original authorized local webhook and its immutable receipt.
2. Import the HMAC-signed final-step assertion from n8n in section 3 of the handoff workbench.
3. In section 4, review the pinned HTTPS host, n8n workflow ID and incoming Webhook node shown in the browser. Re-enter the current owner password.
4. Explicitly approve ONE GET to /api/v1/executions/{numeric-id}?includeData=true using the key held on the local server. The API key and original provider response body are never returned to the browser.
5. Review the durable local result and independently inspect n8n execution history if any mismatch or missing node data is reported. No new webhook, model call, automated repeat, background polling or external write is generated by verification.

**Boundaries:** one network read per signed plan, maximum 8 local checks per UTC day and 100 total. A claim or check interrupted before a response leaves a durable uncertainty record and does not create authority for automatic retry. This deliberately prioritizes a visible owner decision over an uncontrolled retry loop.

## Interpretation of results

| Result | Meaning |
| --- | --- |
| EXECUTION_SUCCESS_CORRELATED | Official provider API confirms correct numeric execution ID, pinned n8n workflow ID, finished=true and status=success; the configured webhook node contains exact signed original incoming delivery/workflow/event |
| EXECUTION_FAILED_CORRELATED | Provider reports a stopped error execution, with correct execution/workflow and matching original inbound delivery; consistent with the earlier signed FAILED claim |
| CLAIM_MISMATCH | Provider execution and inbound delivery match, but API status contradicts the earlier signed final-step outcome; treat as conflict, not success |
| DELIVERY_NOT_CORRELATED | Provider execution was located, but exact saved incoming Webhook node data was absent, ambiguous, or mismatched; no success claim |
| PROVIDER_IDENTITY_MISMATCH | n8n execution ID or n8n workflow ID differs; no success claim |
| PROVIDER_EXECUTION_NOT_FINAL | Provider execution still running or lacks sufficient finalization evidence |
| LOOKUP_NOT_FOUND / LOOKUP_AUTH_REQUIRED / LOOKUP_NETWORK_OR_RESPONSE_UNCERTAIN / LOOKUP_UNCERTAIN | Provider result not conclusively verified; read local ledger and inspect n8n separately |

All records explicitly keep business_effect_verified=false. A successful n8n workflow does **not** prove a downstream business effect, e.g. CRM persistence or actual email delivery. Those require separate read-only downstream provider checks.

## Security, privacy and negative scenarios

- No arbitrary URLs, POST, DELETE, webhook resend or n8n workflow mutation. Only one fixed execution lookup GET to an owner-pinned public HTTPS origin. DNS resolution rejects private/non-global IPs and pins a vetted public IP to TLS with normal hostname certificate verification. Redirects are not followed.
- A hard 1 MiB response limit applies. Raw execution data is processed in memory only, then discarded; the stored receipt contains minimal status metadata, fixed identity fields and SHA-256 evidence digests, never the API key, whole execution JSON or customer content.
- Because includeData=true retrieves stored n8n node outputs, the owner must secure API-key scope, ensure customer data consent, and choose a test workflow before using this with business data. If n8n execution data retention or redaction removes the incoming node output, verification fails closed.
- The security audit accepts only N8N_EXECUTION_READONLY_VERIFY. Owner authentication, CSRF and fresh password are required for the read-only remote check, in addition to the existing signed local receipt gate.
- A saved provider check is persisted BEFORE the GET, and interrupted check states become LOOKUP_UNCERTAIN on startup. No blind retry or silent overwrite of delivery and signed outcome ledgers.
- Read-only history stays local. Stage #111 owner encryption-backed backup can include the SQLite table, subject to separate owner PC recovery verification.

## CI acceptance and unverified live gates

Focused tests run with the pinned AES-GCM dependency across Python 3.11, 3.12 and 3.13, exercising real temporary SQLite, a real encrypted managed connector, signed receipt, authenticated local HTTP, fake API response and stub DNS-pinned TLS. Negative tests cover wrong workflow/execution/delivery, forged Webhook node output, duplicated items, incomplete execution, contradicting signer, malformed target, 404/timeout, query cap, restart quarantine and password/CSRF rejection. Stage #114-#116 regressions and full repo/Chromium acceptance must also pass on the final PR commit.

**Evidence ceiling:** LIVE_N8N_PROVIDER_EXECUTION_VERIFIED=FALSE; INDEPENDENT_BUSINESS_EFFECT_VERIFIED=FALSE; LIVE_WINDOWS_OWNER_RECOVERY_VERIFIED=FALSE; ONLINE_24_7_VERIFIED=FALSE. Do not claim real provider-side verification from synthetic CI.
